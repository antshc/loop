# Research Report: OTel JS SDK on Bun & JSON Logger Parity (issue antshc/loop#112)

## 1. Does OpenTelemetry JS (sdk-trace-base/sdk-node + OTLP/HTTP exporter) work under Bun?

**Short answer: partially, with real, currently-open gaps — manual span creation + the OTLP/HTTP exporter is the safer path; auto-instrumentation is not.**

- OpenTelemetry JS does **not officially support Bun**. On open-telemetry/opentelemetry-js#5260 ("Request timed out" from `@opentelemetry/exporter-trace-otlp-proto`/`-http` under Bun 1.1.31), a project maintainer stated explicitly: *"bun is currently not supported by this project. If you can provide a fix that still passes the tests for Node.js we're happy to accept that fix"* (comment 2024-12-13). The reporter's repro used `OTLPTraceExporter` (proto variant, which shares the `otlp-exporter-base`/`http-transport-utils.js` HTTP-agent code with the `-http` package) and got an immediate `Request timed out` on every export; the collector never received the data. This points at Bun's `node:http` agent/`emitCloseNT` handling diverging from Node's — i.e. exactly the "http agent" class of issue the issue description flags.
- `opentelemetry-js#7226` (opened **Oct 23, 2026** — i.e. this week, confirming the problem is current, not historical) shows `@opentelemetry/instrumentation-http`'s server-span wrapping breaking on Bun 1.4.4+ because Bun changed `https.Server.prototype` to inherit from `http.Server.prototype` (unlike Node, where they're siblings). This causes `instrumentation-http`'s shimmer-based unwrap/rewrap logic to silently drop HTTP server span instrumentation. This is specific to **auto-instrumentation** (`instrumentation-http`), not to manually created spans or the exporter itself, but it confirms Bun's Node-compat layer still diverges in ways that matter for `sdk-node`'s auto-instrumented bundle.
- `oven-sh/bun#39007` (reported against a **1.4.0 canary**, late 2025/2026) shows Bun's `AsyncLocalStorage` (which `@opentelemetry/context-async-hooks`'s `AsyncLocalStorageContextManager` relies on for context propagation) drops the final async stack frame relative to Node — a correctness gap in async-context fidelity, even though basic `run()`/`getStore()` behavior works. Bun's own docs (`bun.com/reference/node/async_hooks`) and community summaries describe `AsyncLocalStorage` as "implemented" but with known edge-case divergences versus Node's V8 promise hooks, particularly with libraries that lean heavily on `async_hooks`.
- No open or closed issue found of a protobuf-serialization-specific failure (the proto variant failure in #5260 was HTTP-transport-level, not protobuf-encoding), and no gzip-specific Bun incompatibility was found in search; these are plausible-but-unconfirmed risk areas, not documented bugs.
- `forceFlush()`/`shutdown()` on process exit: no Bun-specific GitHub issue was found; this is an area to test empirically rather than one with a documented regression.

**Practical implication for loop's design (mirrors `otel.py`'s approach):** building directly on `@opentelemetry/sdk-trace-base` + `BatchSpanProcessor`/`SimpleSpanProcessor` + `@opentelemetry/exporter-trace-otlp-http`, creating spans manually (as `otel.py` does via `tracer.start_span`), and *avoiding* `sdk-node`'s auto-instrumentation (`instrumentation-http`, `registerInstrumentations`) sidesteps the worst documented Bun breakage (#7226) and the context-manager edge case (#39007, which only matters when relying on ALS-based implicit parent-span lookup across deep async chains — `otel.py`'s `_parent_context` logic is a close analogue). The #5260 HTTP-agent timeout is the one real risk for the exporter path itself; it should be smoke-tested against Bun's current stable before relying on it, since it was last confirmed on Bun 1.1.x and may or may not be fixed by late-2026 Bun releases (no closing fix commit was found in the issue thread).

## 2. Span/attribute mapping, `otel.py` → JS SDK

All of `otel.py`'s attributes are plain `gen_ai.*` semantic-convention strings and `loop.*` custom keys (e.g. `gen_ai.operation.name`, `gen_ai.provider.name`, `gen_ai.tool.call.id`, `loop.worktree.path`, `loop.usage.*` — `src/loop/observe/otel.py:109-121, 132-140, 180-193`), so they map 1:1 as plain object keys/values to the JS API's `attributes: Attributes` (`Record<string, AttributeValue>`), since OTel JS attribute value types (`string | number | boolean | Array<...>`) are a superset compatible with the Python values used (`str`, `int`, `bool`, `float` via `_seconds`). No semantic-convention naming divergence exists because loop uses the raw convention strings rather than a language-specific helper constant (Python's `opentelemetry-semantic-conventions` and JS's `@opentelemetry/semantic-conventions` sometimes rename constants, e.g. `ATTR_SERVICE_NAME`, but since `otel.py` writes attribute keys as literals, the JS side can do the same and stay identical).

Gaps to watch:
- **Span kind**: `otel.py` sets `kind=SpanKind.INTERNAL` only for `execute_tool` spans (`otel.py:143`); the `invoke_agent` span and `loop.worktree` span get no explicit kind (defaulting to `INTERNAL` in both SDKs) — this maps cleanly, `SpanKind.INTERNAL` exists identically in JS.
- **Explicit start/end timestamps**: Python passes nanosecond ints via `_nanos()` (`otel.py:30-31`) to `start_time`/`end_time`. The JS API's `startSpan(name, { startTime })` and `span.end(endTime)` accept `[seconds, nanoseconds]` tuples, `HrTime`, `number` (epoch millis), or `Date` — not raw epoch-nanosecond ints — so the nanosecond conversion helper needs a JS equivalent producing a compatible `HrTime`/`Date`, not a direct int port.
- **Status**: `Status(StatusCode.ERROR, message)` / `StatusCode.OK` (`otel.py:72, 157`) map directly to JS's `{ code: SpanStatusCode.ERROR, message }` / `SpanStatusCode.OK`.
- **Metrics**: histograms/counters (`otel.py:163-176`) map directly to `meter.createHistogram`/`createCounter` with the same names/units/descriptions — no gap.
- **Events**: `otel.py` does not use `span.addEvent(...)` anywhere; all data goes in attributes, so there's nothing to reproduce on that front, and no event-specific JS gap exists.
- **No span links** are created in `otel.py`.

Overall, the attribute/span model is faithfully portable; the only real engineering work is the timestamp representation and verifying attribute value-type coercion (e.g. `tool.ok: bool`, `usage.*: int`) round-trips identically through OTLP/HTTP JSON encoding on both sides.

## 3. JSON logger parity (python-json-logger)

Verified from `log.py:11` and `tests/unit/test_logging.py` (`_records`, `_console_handler`):
- **Console** handler format (`log.py:11`): `"%(asctime)s %(levelname)s %(name)s: %(message)s"` — human-readable, not JSON.
- **File** handler (DEBUG-only, `log.py:48-52`): `JsonFormatter()` with **no explicit `fmt`**, so verified empirically (`pythonjsonlogger.core.BaseJsonFormatter.parse()` returns `['message']`), the JSON file records today contain **only `{"message": "<msg>"}** — no level, name, or timestamp field is persisted to the file currently (confirmed by `test_debug_logs_info_and_debug_to_the_console_and_the_json_file` asserting only on `record["message"]`).
- Library logger is silent by default: `logging.getLogger("loop")` gets `NullHandler`-style silence until `configure_logging` is called, verified by `test_the_default_scope_leaves_the_root_logger_and_other_loggers_alone`.

**Recommendation for JS**: given the current field set is minimal (just `message`, optionally extendable to `asctime`/`levelname`/`name`), all three options can reproduce it, but with different effort:
- **pino**: fastest, but its *default* shape (`{"level":30,"time":<epoch-ms>,"pid":...,"hostname":...,"msg":...}`) is numeric-level/epoch-ms and uses `msg` not `message` — needs `messageKey: 'message'`, `base: null` (drop pid/hostname), `formatters.level(label) => ({ level: label.toUpperCase() })`, and `timestamp: () => \`,"asctime":"${new Date().toISOString()}"\`` to match `log.py`'s field names/levels exactly. Very fast, but requires several option overrides for exact parity.
- **winston**: `combine(timestamp(), json())` plus a custom format function is more directly declarative for field renaming (`message`, `level`, `name`) and silencing a named child logger (`winston.loggers.get('loop')` with no transports = silent until configured) maps naturally onto the "library logger silent until host configures" requirement mirrored in `test_the_default_scope_leaves_the_root_logger_and_other_loggers_alone`. Slightly more verbose, less raw throughput than pino.
- **LogTape**: designed explicitly for library authors (silent-until-configured hierarchical loggers), closest conceptual match to Python's logger-hierarchy/propagate model (`log.py:34`, `logger.propagate = False`), but its JSON formatting is less customizable out of the box than pino/winston and is a newer/smaller ecosystem.
- **Custom minimal logger**: Given only one field (`message`) is emitted today, a ~20-line wrapper (`console.error(JSON.stringify({message}))` plus a stderr formatter for console) would trivially match current behavior and avoid a dependency, at the cost of reimplementing level filtering/propagation semantics by hand.

**Recommendation**: use **winston** for the JS port — its named/child-logger model and declarative field renaming most directly mirror `log.py`'s `logging.getLogger(name)` + handler-replacement + `propagate=False` pattern, and today's thin field set (`message` only) needs no exotic formatter work. Revisit pino if raw throughput becomes a bottleneck, since it can be configured to match exactly as well, just with more formatter boilerplate.
